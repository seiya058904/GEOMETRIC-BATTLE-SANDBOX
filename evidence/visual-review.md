## 待机缓存验证结论

只有 `PREPARING` 且军阵是冻结的不可变对象时，渲染器才保留完全相同的上一帧。实际编辑器修改军阵时发布新对象；选择集合和预览数组也由编辑器/输入模块替换，因此可以用对象身份检查这些内容的变化。

真实浏览器执行 34 项检查：相同参数的待机帧不再提交 Canvas 重画；相机平移/缩放、视口尺寸、画质、悬停兵种/位置/阵营/方向/合法性/单位 ID、悬停移除、预览替换/移动/清空、选择替换/清空、框选位置、自由部署区域提示、网格、生命显示和军阵对象更新均触发重画。可变测试军阵每次都重画。`FIGHTING` 和 `PAUSED` 即使模拟时间相同也每次重画，没有引入战斗帧复用。

这只验证缓存路径与失效条件，不把待机低开销称为战斗性能提升。这项缓存检查完成后，完整 FIGHTING 性能仍由独立主流程测试负责；后续网格补丁没有改变待机缓存条件。

## 独立性能定位后的网格补丁

首轮视觉通过后，主流程用真实 200 人战斗进行了网格开关对照。修复前原始数据已保存在 `grid-diagnostic-before/browser-diagnostic.json` 和 `grid-diagnostic-before/browser-diagnostic-no-grid.json`，不会用后续结果覆盖。

| 修复前对照条件 | 墙钟时长 | 实际模拟推进 | 平均 FPS |
| --- | --- | --- | --- |
| low，网格开启 | 12.0467 秒 | 3.7667 秒 | 16.5752 |
| low，网格关闭 | 12.0090 秒 | 10.6667 秒 | 51.9409 |

这是定位瓶颈的开关对照，**51.94 FPS 不是新图案实现的性能结果**。两组起始编队相同，结束时存活数量不同，因为模拟推进时间不同。修复前诊断没有 JS LongTask，主界面更新的累计时间也很低；结合每帧约千余次小矩形提交，网格成为明确的修复目标。

`Renderer._field` 原来逐点调用 `fillRect`，现在改为一个透明 Canvas 重复图案，每帧只用一次矩形填充绘出网格。保留原来的网格间距选择、颜色和点大小公式；图案按整数像素尺寸反算世界变换，点中心仍落在世界坐标 `n × spacing`。普通缩放时点约 0.9 CSS 像素，最大放大时仍遵守旧公式的 0.55 世界单位下限。平移不重建图案，缩放、间距或 DPR 变化时替换当前图案，始终只保留一个缓存，瓦片边长最多 116 像素。

新增 `tests/render-grid.test.js`，仅运行 Node 记录式 Canvas fixture，8 / 8 通过：桌面、手机竖屏、手机横屏、最小/最大缩放、1.5 DPR、平移和缩放缓存失效、网格开关。额外连续改变缩放 120 次，检查单一当前图案和尺寸上界。测试同时核对点大小、世界原点、重复周期和每帧只有一次网格填充。这是几何和提交数量验证，不把它称为真实浏览器栅格视觉或 FPS 验证。

主流程随后独占运行 100 对 100 复测，网格补丁单独启用时仍出现数秒间隔，因此不能宣称网格图案本身已经改善实测 FPS。此补丁没有修改单位几何、兵种数值、世界尺寸、模拟或 UI。

## Canvas 上下文配置的阶段实测记录

网格提交数量减少后仍存在长间隔，主流程进一步隔离 Canvas2D 的呈现与绘制配置。这里只记录已完成的测量，不把 JavaScript 绘制提交时间当作栅格化和合成完成时间。

主画布先加入 `willReadFrequently: true`，随后完整矩阵归档于 `main-canvas-hint-matrix/browser-performance.json`。该矩阵在 20、200、600 人场景测得约 59.59、53.94、33.12 FPS，实际模拟速度均接近 1×；1000 和 1200 人进入低画质图块绘制路径后，仍出现数秒级间隔。随后一场极端特效的长间隔是否受前场资源状态影响，没有被单独证实。

针对低画质的 `_unitSprite → drawImage` 路径，主流程把网格瓦片、单位图块及菜单图标的上下文也设为 `willReadFrequently: true`，与主画布请求一致的绘制倾向。静态源继续使用默认透明通道，没有引入不透明底块，也没有改变图形、画质选择、DPR、单位规则或模拟精度。

| 1000 人运行记录 | 平均 FPS | 实际模拟速度 | 最大 RAF 间隔 | 证据 |
| --- | --- | --- | --- | --- |
| 仅主画布请求该配置，完整矩阵内运行 | 26.31 | 0.483× | 2316.5ms | `main-canvas-hint-matrix/browser-performance.json` 的 `500-vs-500` |
| 主画布和静态源均请求该配置，独立单场 | 25.10 | 0.987× | 266.6ms | `performance-500-vs-500.json` |

**这两条记录不构成平均 FPS 提高的证据。** 新单场的实际模拟速度接近正常，并且该次采样没有旧记录中的数秒停顿。旧值来自顺序矩阵，新值来自独立场景，运行顺序和资源状态不同；不能只凭两者对比，就断言已证明跨后端读回或前场 GPU 队列是唯一根因。完整规模与长期运行结论仍由主流程报告提供。

该属性是浏览器标准提示，不能仅凭 `getContextAttributes()` 返回 true 就宣称跨浏览器已强制使用物理 CPU 后端，更不能外推 CPU 绘制在所有实体 GPU 设备上都更快。标准说明见 [WHATWG Canvas settings](https://html.spec.whatwg.org/multipage/canvas.html#concept-canvas-will-read-frequently)，实现背景见 [Chrome Canvas2D 文档](https://developer.chrome.com/blog/canvas2d)。源画布属性应在首次取得上下文时设置；本轮没有新增用户操作或浏览器启动参数依赖。

## 复现方法

必要脚本已归入项目，使用共享 `tests/browser-runtime.mjs`，不包含云端浏览器、字体或 QA 运行时依赖。通过 README 中的 Playwright 安装方式配置后，可以运行 `node tests/render-gallery.mjs` 重建图鉴、视野裁剪、对象兼容、1200 单位几何缓存及音频基础检查；运行 `node tests/render-cache.mjs` 复现 34 项待机缓存检查。这两个脚本从原来已执行的临时脚本提取并改为共享运行时；归档时只作语法核对，没有再次运行浏览器或扩大测试范围。

相机 200 次坐标往返等基础数学检查来自临时 Node 执行：创建相机，验证 worldToScreen → screenToWorld 恢复输入点；缩放前后同一 CSS 指针的世界锚点保持；pan 使用 CSS 像素差；resize 后坐标转换仍可逆；非法缩放因子不会改变状态。最终完整游戏截图通过 Playwright/CDP 拍摄并人工打开，上述图鉴脚本不能替代主页面与实际战斗验收。

## 性能和验收边界

渲染只读取模拟，不推进或更改位置、生命、碰撞、胜负、随机数。动画读取 `sim.time`，没有独立 RAF 或粒子计时器。自动高/中/低画质的 DPR 上限分别为 2 / 1.5 / 1；视野外单位仍参与模拟；特效有总预算和地面预算，关键反馈优先。

低画质的小单位复用程序化透明几何缓存，保留两个攻击姿势；坦克独立炮塔保持实时绘制，放大或选中时恢复实际几何细节。合成 1200 单位场景确认缓存有界、可见单位全部绘出，该场景不代表完整游戏 FPS。音频最多 10 个并发、每次最多 5 个，按类型限频，事件历史有界。
